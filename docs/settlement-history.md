# 정산 기록과 결제 생명주기

이 문서는 Lightning Split의 정산 기록 기능과 Lightning invoice 재발급·늦은 결제 추적 규칙을 정의합니다.

## 목표

정산 기록은 단순한 과거 로그가 아니라 카카오페이식 정산 현황의 역할을 합니다.

1. 정산을 시작하면 현재 정산 세션이 기기에 저장됩니다.
2. 한 명이라도 미정산이면 현재 정산은 계속 진행 중입니다.
3. 결제 요청이 만료된 참여자는 해당 슬롯의 새 Lightning invoice를 발급하고 새 QR을 다시 공유할 수 있습니다.
4. 모든 참여자의 결제가 자동 확인되거나 운영자가 받는 지갑에서 직접 확인한 뒤에만 정상적인 `새 정산` 전환이 허용됩니다.
5. 완료된 정산은 표시용 기록으로 보관한 뒤 새 정산을 시작합니다.

## 진행 중 정산

진행 중 정산은 기존 active-session 저장소를 그대로 사용합니다. 현재 invoice와 재발급된 이전 invoice의 결제 확인 정보가 필요한 동안에는 기존 settlement polling 로직이 현재 세션과 `invoiceHistory`를 함께 확인합니다.

만료된 invoice는 결제가 불가능하다고 단정하지 않습니다. 최종 확인 유예와 과거 invoice 보존 기간 동안 LUD-21 확인이 가능한 경우 늦게 관찰되는 결제를 계속 확인합니다.

`새 정산`은 미정산 슬롯이 있으면 현재 정산을 버리지 않습니다. 대신 사용자를 첫 미정산 슬롯으로 이동시키고, 만료된 결제 요청을 재발급·재공유하도록 안내합니다.

## 명시적 정산 중단

진행 중 정산을 강제로 삭제하는 것은 정상 흐름과 별개의 예외 동작입니다.

- 아직 결제 가능한 invoice가 있어도 Lightning 네트워크의 결제 요청 자체가 취소되는 것은 아닙니다.
- 현재 세션을 삭제하면 앱이 이후 늦은 입금을 자동 확인할 근거도 사라질 수 있습니다.
- 따라서 진행 중 정산 삭제는 `정산 중단·삭제`로 명시하고 강한 확인 문구를 사용합니다.

## 완료 기록

장기 표시용 완료 기록에는 다음 정보를 저장합니다.

- 입력 통화와 총액
- 총 참여자 수와 결제 요청 수
- 정산 메모
- 참여자 표시 이름
- 각 참여자의 법정화폐 몫과 sats
- 자동 확인·직접 확인 상태와 완료 시각
- 당시 invoice 만료 시각
- 교체된 이전 결제 요청에서 뒤늦은 입금이 확인된 경우 그 경고 시각

장기 표시용 기록에는 다음 결제 민감정보를 저장하지 않습니다.

- Lightning Address
- BOLT11 원문
- payment hash
- verification token
- provider domain

완료 기록은 최대 200건을 유지합니다.

## 완료 후의 제한적 임시 추적

정산이 완료되더라도 다음 두 경우에는 짧은 기간 동안 추가 확인이 필요할 수 있습니다.

1. 직접 확인으로 완료 처리했지만 LUD-21 자동 확인이 가능한 현재 invoice
2. 재발급으로 교체했으며 아직 결제 여부가 확정되지 않은 이전 invoice

이 경우 표시용 기록과 별도의 IndexedDB store에 필요한 최소 결제 확인 정보만 임시 보관합니다. 보관 기한은 해당 invoice의 만료 시각에 `settlementHistoricalRetentionSeconds`를 더한 시각까지이며, 현재 정책에서는 최대 7일입니다.

앱이 열려 있고 화면이 보이는 동안 이 임시 정보를 이용해 약 60초 간격으로 다시 확인합니다. PWA가 종료된 상태에서 iOS가 임의의 백그라운드 실행을 보장한다고 가정하지 않습니다. 앱이 다시 열리거나 온라인·가시 상태로 돌아오면 확인을 재개합니다.

- 직접 확인했던 현재 invoice가 네트워크에서 확인되면 완료 기록을 `자동 확인 완료`로 승격합니다.
- 교체된 이전 invoice의 결제가 뒤늦게 확인되면 완료 기록에 `중복 입금 가능성` 경고를 남깁니다.
- 보관 기한이 지나면 임시 결제 확인 정보는 삭제하고 표시용 기록만 남깁니다.
- 완료 기록을 삭제하면 연결된 임시 추적 정보도 함께 삭제합니다.

## QR 공유

현재 유효한 invoice만 공유할 수 있습니다. 공유 순서는 다음과 같습니다.

1. QR PNG 이미지 + 결제 요청 텍스트
2. 이미지 파일 공유가 불가능하거나 실패하면 동일한 결제 요청 텍스트만 native share
3. native share도 사용할 수 없으면 결제 요청 텍스트를 클립보드에 복사

QR PNG는 P2P Check에서 이미 사용하는 패턴과 동일하게 Canvas에서 `Blob`으로 직접 변환한 뒤 `File`을 만듭니다. `data:` URL을 다시 `fetch()`하여 파일로 바꾸는 우회 경로는 사용하지 않습니다.

사용자가 공유 시트를 닫은 `AbortError`만 명시적인 취소로 처리합니다. 파일 공유의 기타 실패는 텍스트 공유로, 텍스트 공유의 기타 실패는 클립보드로 내려갑니다.

## 레이아웃 규칙

이 기능에서 추가하는 최상위 화면 블록은 개별 `margin`을 임의로 덧붙이는 대신 공통 spacing token과 stack `gap`을 사용합니다.

- 4px: `--space-1`
- 8px: `--space-2`
- 12px: `--space-3`
- 16px: `--space-4`
- 20px: `--space-5`
- 24px: `--space-6`
- 홈의 주요 블록 사이: `--space-section` = 12.8px

특히 홈 화면의 `정산 기록 보기`, 금액 입력 카드, 정산 미리보기, 경고, 시작 버튼은 `home-action-stack`의 동일한 `gap` 규칙을 따릅니다. 새 블록을 추가할 때 이들 사이를 다시 개별 margin 값으로 맞추지 않습니다.
